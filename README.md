# BackgroundService в ASP.NET Core

Код к видео «BackgroundService в ASP.NET Core — полный гайд» с канала «Папочка Разработки».

Внутри API интернет-магазина на .NET 10 и PostgreSQL. Магазин принимает заказы и шлёт покупателю письмо о заказе, сам отменяет неоплаченные заказы и считает продажи за день. Менеджер выгружает заказы в CSV, страница товара считает просмотры, а хелсчеки говорят дежурному, когда фоновая работа встала.

У каждого раздела видео свой тег. Переключись на тег раздела, и перед тобой ровно тот код, что был на экране в конце раздела. Сломать его можно так же, как в видео.

## Запуск

Нужен Docker.

```
docker compose up --build
```

- магазин: http://localhost:8080
- почта, тестовый smtp4dev (сюда приходят все письма магазина): http://localhost:8025

Магазин в compose работает в дев-режиме (`ASPNETCORE_ENVIRONMENT: Development`): на старте контейнер зависимостей проверяет время жизни сервисов. Как посмотреть прод, сказано в разделе 3.

Из IDE: подними только базу и почту (`docker compose up db mail`) и запусти `src/Shop`. Магазин будет на http://localhost:5080 (поменяй `@shop` в `requests.http`).

## Запросы

Проще всего через `requests.http` (VS Code с REST Client, Rider, Visual Studio). Или из консоли.

bash, Git Bash, macOS, Linux:

```
curl -X POST http://localhost:8080/orders -H "Content-Type: application/json" -d @tools/order.json
curl -X POST http://localhost:8080/chaos/mail/fail-next
```

PowerShell:

```
Invoke-RestMethod -Method Post http://localhost:8080/orders -ContentType application/json -Body (Get-Content tools/order.json -Raw)
Invoke-RestMethod -Method Post http://localhost:8080/chaos/mail/fail-next
```

С раздела 2 в `tools/` лежат запросы к базе магазина. Выполняются так:

```
docker compose exec -T db psql -U shop < tools/outbox.sql
```

В PowerShell: `Get-Content tools/outbox.sql | docker compose exec -T db psql -U shop`.

## Как ломать

### Сбои

Сбой включается запросом к магазину и живёт в памяти процесса. У второго инстанса свой адрес (`http://localhost:8082/chaos/...`), а рестарт снимает все сбои.

| Запрос | Что ломает | С раздела |
|---|---|---|
| `POST /chaos/mail/fail-next` | следующее письмо получит ошибку почты (`SmtpException`) | 1 |
| `POST /chaos/mail/slow?seconds=9` | почта отвечает медленно, столько секунд на каждое письмо | 1 |
| `POST /chaos/mail/up` | почта снова работает, все сбои почты сняты | 1 |
| `POST /chaos/crash-after-save` | процесс упадёт сразу после следующего сохранения в базу (`Environment.FailFast`) | 2 |
| `POST /chaos/mail/down` | почта лежит: каждое письмо получает `SmtpException` | 5 |
| `POST /chaos/mail/silent` | почта принимает соединение и молчит, отправка ждёт ответа, пока её не оборвёт таймаут | 5 |
| заказ из `tools/order-typo.json` | адрес на `.invalid`: ящика нет, почта отвечает ошибкой на каждую попытку | 5 |
| `POST /chaos/crash-after-send` | процесс упадёт сразу после следующей отправки, раньше, чем рассылка сохранит отметку | 8 |
| `POST /chaos/pay/slow?seconds=70` | оплата ждёт перед сохранением (только у привычной оплаты, анти-пример `LoadModifySavePay`) | 11 |
| `POST /chaos/cleanup/slow?seconds=70` | очистка ждёт перед сохранением (только у анти-примера `LoadModifySave`) | 11 |
| `POST /chaos/db/ok` | сбои базы сняты | 11 |
| `POST /chaos/export/slow?seconds=5` | каждая часть выгрузки (тысяча заказов) пишется столько секунд | 13 |
| `POST /chaos/db/slow-views?seconds=30` | запись просмотров в базу ждёт столько секунд, как база на распродаже | 14 |
| `POST /chaos/views/flood?count=1000000` | столько просмотров разом, как поток страниц на распродаже | 14 |

| `POST /chaos/cleanup/fail` | проход очистки падает на каждом тике, снимается `POST /chaos/db/ok` | 15 |

Медленная почта ждёт внутри отправки. С раздела 5 у отправки свой таймаут, и всё, что дольше десяти секунд, он обрывает, как обрывал бы настоящую медленную почту.

### Анти-примеры

Ошибки из видео лежат в `src/Shop/Mistakes/`, по файлу на ошибку, и включаются настройкой `Mistakes__Имя=true`. Анти-пример подменяет настоящий код: фоновый сервис, почту, канал или действие контроллера с тем же маршрутом.

Создай рядом с `docker-compose.yml` файл `docker-compose.override.yml`, Docker Compose подхватит его сам:

```
services:
  shop:
    environment:
      Mistakes__TaskRunScoped: "true"
```

и перезапусти: `docker compose up -d --build`.

С раздела 7 у магазина бывает второй инстанс `shop2`. Ему ту же настройку ставят отдельно, под `shop2`, а поднимают оба с `--build`: у каждого свой образ, и `docker compose up --build shop` второй не пересоберёт. Файла override в репозитории нет (он в `.gitignore`), поэтому при переходе на другой тег он остаётся. Закончил, удали его. Из IDE настройка та же, в переменных окружения или в `appsettings.json`: `"Mistakes": { "TaskRunScoped": true }`.

## Разделы

### 01-task-run · Почему не Task.Run из контроллера

Что изменилось. Контроллер сохраняет заказ контекстом базы запроса, отдаёт отправку письма в `Task.Run` и сразу отвечает. После отправки лямбда ставит в заказе время отправки (`EmailSentAt`) и сохраняет тем же контекстом (`Api/OrdersController.cs`, `Create`). Почта магазина: `IOrderMail` с одним методом (`Mail/IOrderMail.cs`), у каждого письма свой `SmtpClient`. Оплата (`POST /orders/{id}/pay`) пока написана привычно: загрузить, проверить, поменять, сохранить. Ею займётся раздел 11.

Что попробовать:

1. Оформи заказ. Письмо придёт в почту, http://localhost:8025.
2. Открой заказ: `GET /orders/{id}`. Поле `emailSentAt` пустое, отметки нет.
3. В логе магазина (`docker compose logs shop`) ни строки об ошибке. А сохранение отметки бросило `ObjectDisposedException`: контекст задиспоужен вместе со scope запроса. Исключение лежит в таске, которую никто не ждёт.
4. Починка на месте: анти-пример `Mistakes__TaskRunScoped` (`Mistakes/TaskRunScoped.cs`). Лямбда открывает свой scope и ловит ошибку. Оформи заказ: `emailSentAt` заполнено. Теперь `POST /chaos/mail/fail-next` и ещё заказ: в логе «Письмо к заказу … не ушло».
5. Деплой с тем же анти-примером. `POST /chaos/mail/slow` (письмо уходит девять секунд), оформи заказ и сразу останови магазин: `docker compose stop shop`. Он останавливается за секунду: хост о лямбде не знает и её не ждёт. Подними магазин (`docker compose start shop`). Письма нет ни в почте, ни в логе, отметки в заказе нет. Медленная почта после рестарта снялась сама.

Дальше:

- Предел для `Task.Run` можно поставить семафором, тогда фон не займёт весь пул. Деплой так не закрыть: хост о такой работе не знает и при остановке её не ждёт.
- Здесь у каждого письма свой `SmtpClient`. Если сделать клиент общим на всё приложение, параллельные `Task.Run` сломают его первыми. `SmtpClient` шлёт одно письмо за раз, второе в ту же секунду получит `InvalidOperationException: An asynchronous call is already in progress`, и это исключение тоже останется в таске, которую никто не ждёт. Подробно в разделе 9.
- Контексты в пуле (`AddDbContextPool`). После ответа контекст не диспоузится, а возвращается в пул, сбрасывает всё, что отслеживал, и достаётся следующему запросу. Лямбда поставит отметку заказу, о котором контекст уже забыл, и сохранение ничего не запишет. Или запишет чужие изменения раньше времени, или упадёт: одним контекстом сразу пользуются лямбда и чужой запрос.

### 02-outbox · Письмо в таблицу вместе с заказом

Что изменилось. `Task.Run` ушёл. Контроллер добавляет в контекст заказ и строку письма (`Data/PendingEmail.cs`: ссылка на заказ, адрес, время создания, время отправки) и зовёт `SaveChanges` один раз. Одна транзакция пишет либо обе строки, либо ни одной. Такую таблицу исходящих называют outbox. Отметка об отправке переехала из заказа в строку письма (`SentAt`), а текст письма из заказа соберёт тот, кто отправляет. На этом теге письма ещё никто не отправляет: строка ждёт фоновый сервис раздела 3.

Что попробовать:

1. Оформи заказ и посмотри таблицу: `tools/outbox.sql` (как выполнить, сказано в «Запросах»). Строка письма с пустым `SentAt`, заказов без письма нет.
2. Падение после сохранения: `POST /chaos/crash-after-save` и заказ. Процесс падает сразу после `SaveChanges`. Ответа не будет, магазин поднимется сам (`restart: on-failure`). В таблице и заказ, и строка письма: письмо ждёт отправки.
3. Анти-пример `Mistakes__SendAfterSave` (`Mistakes/SendAfterSave.cs`): письмо прямо в запросе, сразу после сохранения. Повтори п. 2. Заказ в базе есть (`tools/outbox.sql`, «заказ без письма»), письма в почте нет, и ни один код к этому заказу больше не вернётся.

Дальше:

- У нас заказ и письмо сохраняются одним `SaveChanges`, это одна транзакция. Если сохраняешь несколькими вызовами `SaveChanges`, оберни их в явную транзакцию (`Database.BeginTransactionAsync`). С включённым `EnableRetryOnFailure` явная транзакция падает, пока не обернёшь её в `Database.CreateExecutionStrategy().ExecuteAsync(...)`.
- Что хранить в строке: ссылку на заказ или готовый текст. У нас ссылка, и текст собирается при отправке, так что письмо покажет заказ таким, какой он в момент отправки. Это бывает плохо. Почта лежит, письмо о заказе ждёт повтора и уходит через полчаса (раздел 5), а очистка за это время отменила неоплаченный заказ (раздел 10). Покупатель получает «заказ принят» о заказе, который уже отменён. Нужен заказ на момент оформления, клади в строку готовый текст. Нужно не слать письмо об отменённом, проверяй статус перед отправкой.
- Готовый outbox есть в библиотеках для шин сообщений: MassTransit, Wolverine, CAP. Строка сообщения пишется в той же транзакции, а библиотека сама доставляет её в брокер (RabbitMQ, Kafka). Нашему магазину брокер не нужен: у него одна база и одна почта, и таблица исходящих с фоновым сервисом делает то же без лишней системы.

### 03-worker · Фоновый сервис, который отправляет

Что изменилось. Фоновый сервис `Background/EmailOutboxWorker.cs` наследует `BackgroundService` и крутит цикл на `PeriodicTimer`. Раз в пять секунд проход открывает свой scope, берёт из него контекст базы, выбирает до двадцати писем с пустым `SentAt`, шлёт каждое, ставит отметку и сохраняет. Регистрация: `AddHostedService` в `Program.cs`. Почту (`IOrderMail`, singleton) и фабрику scope (`IServiceScopeFactory`) сервис берёт в конструктор. Контекст базы берётся только из scope прохода.

Что попробовать:

1. Оформи заказ. Письмо придёт в течение пяти секунд, а у строки в `tools/outbox.sql` появится `SentAt`.
2. Анти-пример `Mistakes__DbInConstructor` (`Mistakes/DbInConstructor.cs`): контекст базы в конструкторе фонового сервиса. Магазин не стартует: `Cannot consume scoped service 'Shop.Data.AppDb' from singleton 'Microsoft.Extensions.Hosting.IHostedService'`, и Docker поднимает его по кругу (`docker compose ps` показывает `Restarting`).
3. Тот же анти-пример в проде: добавь в override `ASPNETCORE_ENVIRONMENT: Production`. Магазин стартует, письма уходят. Но после каждого прохода в логе «Контекст рассылки держит объектов: …», и число только растёт. Один контекст на всю жизнь процесса помнит каждое письмо и каждый заказ, которые загрузил.
4. `Mistakes__StartAsyncLoop` (`Mistakes/StartAsyncLoop.cs`): свой `IHostedService` с циклом прямо в `StartAsync`. Письма уходят, а магазин не отвечает на запросы. Строки `Now listening` в логе нет, ошибки тоже.
5. `Mistakes__ExitingLoop` (`Mistakes/ExitingLoop.cs`): цикл «пока есть письма». На свежей базе (`docker compose down -v`) он кончается сразу на старте. Оформи заказ: магазин отвечает, письмо не уходит, в логе тихо.

Дальше:

- Почему `BackgroundService`, а не свой `IHostedService`. Хост вызывает `StartAsync` каждого сервиса по очереди, ждёт его и только потом запускает веб-сервер. Цикл в `StartAsync` не вернётся никогда (п. 4). `BackgroundService.StartAsync` запускает `ExecuteAsync` и сразу возвращается.
- Цикл, который кончается сам (п. 5). Вернулся `ExecuteAsync`, и хост считает работу сделанной и заново его не запустит. Цикл фонового сервиса кончается только по стоппинг-токену.
- `Task.Delay` против `PeriodicTimer`. Цикл с `await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken)` тоже годится, только пауза отсчитывается от конца прохода, и запуски понемногу съезжают. `PeriodicTimer` тикает от своего создания, а тики, пропущенные за долгий проход, не копятся. Только не `Thread.Sleep`: он держит поток пула всю паузу.
- `IDbContextFactory`. Если проходу нужен только контекст базы, фабрика контекстов (`AddDbContextFactory`) создаёт его без scope. Если в проходе участвуют другие scoped-сервисы, например репозитории, нужен scope.
- `AsNoTracking`. Строки писем рассылка меняет, поэтому контекст их отслеживает. То, что только читаешь, читай с `AsNoTracking`: контекст не держит копию объекта и не сравнивает её при сохранении.
- Синхронное начало `ExecuteAsync`. На .NET 8 и 9 код в начале `ExecuteAsync`, до первого `await`, выполнялся синхронно и задерживал старт приложения. С .NET 10 хост запускает весь `ExecuteAsync` в фоне, но тяжёлая синхронная работа всё равно занимает поток пула.
- В конструктор фонового сервиса бери только singleton. Scoped-сервис в конструкторе singleton в проде проживёт всю жизнь процесса (п. 3). Transient тоже, и его проверка дев-режима не остановит.
- Тест цикла без ожидания. Таймер умеет брать время не из часов системы, а из `TimeProvider`: в сервисе `new PeriodicTimer(TimeSpan.FromSeconds(5), time)`, где `time` получен из конструктора как `TimeProvider` (в `Program.cs` это `AddSingleton(TimeProvider.System)`). В тесте берёшь `FakeTimeProvider` из пакета `Microsoft.Extensions.TimeProvider.Testing`, и тик наступает, когда скажет тест:

  ```csharp
  var time = new FakeTimeProvider();
  var mail = new FakeMail(); // запоминает, что отправлено
  var worker = new EmailOutboxWorker(scopes, mail, time);
  await worker.StartAsync(default);

  time.Advance(TimeSpan.FromSeconds(5)); // тик — без пяти секунд ожидания
  await mail.WaitForAsync(count: 1);
  await worker.StopAsync(default);
  ```

  `scopes` здесь фабрика scope из `ServiceCollection` с контекстом на тестовой базе (Testcontainers или SQLite). Так же тестируется повтор из раздела 5, если и время попытки рассылка берёт из того же `TimeProvider` (`time.GetUtcNow()` вместо `DateTime.UtcNow`): сдвинул время на минуту, и письмо пробует снова.

### 04-try · Исключение в фоне

Что изменилось. В рассылке два `try`, оба внутри цикла. Первый стоит вокруг одного письма: ошибка почты уходит в лог с номером заказа, цикл идёт к следующему письму, а это остаётся в таблице без отметки. Второй стоит вокруг всего прохода и ловит то, что случилось вне письма, например базу, которая не ответила на выборку. У второго `catch` фильтр по стоппинг-токену: отмену при остановке он пропускает. Логгер сервис получает в конструкторе.

Что попробовать:

В логе две строки: `fail: … BackgroundService failed` и `crit: … The HostOptions.BackgroundServiceExceptionBehavior is configured to StopHost`. Магазин остановился целиком и не отвечает. `docker compose ps -a` показывает `Exited (0)`: для Docker это штатный выход, и `restart: on-failure` его не поднимает. Поднять руками: `docker compose up -d shop`.

Не ровно раз в пять: подключение к лежащей базе само тянется несколько секунд, а тики, пропущенные за это время, `PeriodicTimer` не копит. `docker compose start db`, и проходы снова идут.

Дальше:

- Что хост делает с упавшим фоновым сервисом, решает `HostOptions.BackgroundServiceExceptionBehavior`: `StopHost` (по умолчанию с .NET 6) или `Ignore`. С `Ignore` магазин живёт, а упавший сервис мёртв: хост его не перезапускает.

- `try` вокруг всего цикла, снаружи `while`. Первая же ошибка выходит из цикла, ты её логируешь, `ExecuteAsync` возвращается без ошибки, и хост его заново не запустит. Рассылка мертва, только тихо: магазин работает, письма копятся.

### 05-retry · Письмо, которое не ушло

Что изменилось. В строке письма два новых поля. `Attempts` считает, сколько раз почта ответила ошибкой, `NextTryAt` говорит, раньше какого времени письмо не брать. Предел задаёт `PendingEmail.MaxAttempts`, пять. Выборка берёт письмо, только если оно не отправлено, у него меньше пяти попыток и его время пришло. На ошибке `ScheduleRetry` добавляет попытку и отодвигает следующую на квадрат числа попыток в минутах: 1, 4, 9, 16. Промежуточную ошибку он пишет предупреждением (`warn`), пятую ошибкой (`fail`). После пятой письмо выходит из выборки и ждёт человека: `POST /outbox/given-up/retry` (`Api/OutboxController.cs`) одной командой сбрасывает попытки всем сдавшимся. У отправки свой таймаут, десять секунд токеном (`Mail/SmtpOrderMail.cs`), и почта, которая молчит, становится обычной ошибкой. Частичный индекс по `NextTryAt` хранит только письма, которые ждут (`Data/AppDb.cs`).

Что попробовать:

1. Почта лежит: `POST /chaos/mail/down` и заказ. Через пять секунд в `tools/outbox.sql` у письма одна попытка и время следующей через минуту. В логе одна строка `warn`, а не стена ошибок каждые пять секунд. Подними почту (`POST /chaos/mail/up`), и письмо уйдёт на своей следующей попытке.
2. Долгая авария за минуту. Снова `POST /chaos/mail/down` и заказ. Паузы ждать не нужно: `tools/skip-wait.sql` ставит всем неотправленным время следующей попытки «сейчас». Выполни его четыре раза, каждый раз после тика (секунд через шесть). После пятой ошибки в логе `fail`, а в `tools/outbox.sql` «сдались, ждут разбора: 1». Подними почту: письмо само не уйдёт. `POST /outbox/given-up/retry` отвечает, сколько писем вернул, и на ближайшем тике письмо уходит.
3. Опечатка в адресе: заказ из `tools/order-typo.json` (адрес на `.invalid`, `SmtpFailedRecipientException`). Почта работает, а это письмо ошибается на каждой попытке и после пятой выходит из выборки. Остальным письмам оно не мешает. Команда возврата вернёт и его, и оно снова сдастся, пока адрес не исправят (запросы в конце `tools/outbox.sql`).
4. Почта молчит: `POST /chaos/mail/silent` и заказ. Через десять секунд после тика в логе `warn` с `OperationCanceledException`: таймаут оборвал отправку, и письмо получило попытку и паузу, как при любой ошибке. Без своего таймаута отправку держал бы таймаут клиента, сто секунд на письмо.
5. Анти-пример `Mistakes__RetryEveryTick` (`Mistakes/RetryEveryTick.cs`): рассылка раздела 4, `try` есть, повтора нет. `POST /chaos/mail/down`, и каждые пять секунд по ошибке на каждое письмо. Ещё нагляднее с плохими адресами. На свежей базе выполни `tools/seed-typos.sql` (двадцать писем на `typo@example.invalid`, созданных час назад) и оформи заказ. Твоё письмо не уходит никогда: батч каждый раз берёт двадцать самых старых, а это двадцать плохих. Выключи анти-пример, и письмо уйдёт через пару тиков: плохие после первой ошибки ушли в паузу.

Дальше:

- Временная ошибка против постоянной. У SMTP коды 4xx временные (ящик переполнен, сервер занят), 5xx постоянные (ящика нет). Постоянную незачем повторять пять раз: письмо на несуществующий адрес можно сразу пометить сдавшимся (`Attempts = MaxAttempts`) и не тратить полчаса. В `System.Net.Mail` для этого есть `SmtpFailedRecipientException` и его `StatusCode`.
- Готовые повторы есть в Polly и `Microsoft.Extensions.Resilience`: повтор с паузой, предел, размыкатель. Они повторяют в памяти, внутри одного вызова. Повтор, который переживает рестарт и полчаса аварии, живёт в строке письма, как здесь.
- MailKit против `System.Net.Mail.SmtpClient`. Microsoft не рекомендует `SmtpClient` для новой разработки и советует MailKit: современные протоколы, TLS, одно соединение на много писем. Для тестовой почты smtp4dev хватает и стандартного клиента. В проде хост, порт, TLS и учётные данные берутся из настроек (`MailSettings`), пароль из хранилища секретов.
- Таймаут самого клиента. `SmtpClient.Timeout` (по умолчанию сто секунд) асинхронная отправка соблюдает только с .NET 10, на .NET 8 и 9 `SendMailAsync` его не видит. Токен из `CancellationTokenSource` работает на любой версии, поэтому таймаут здесь токеном.
- Адрес команды возврата служебный, и в проде он не открыт всем: `[Authorize]` с ролью дежурного или отдельный порт для служебных адресов.
- Письмо с адресом, который не исправить, удаляют руками. Адрес исправили, сбрасывают попытки (запросы в конце `tools/outbox.sql`).
- Тест повтора без ожидания минут делается на `FakeTimeProvider`, как в «Дальше» раздела 3.

### 06-shutdown · Остановка при деплое

Что изменилось. Первая строка цикла писем проверяет стоппинг-токен: пришла остановка, и новое письмо не начинаем. Сохранение отметки идёт с `CancellationToken.None`. Письмо, которое уже ушло, отменить нельзя, значит, и его отметку тоже. Отправка токена не получает, её держит свой таймаут в десять секунд. Таймаут остановки хоста 20 секунд (`HostOptions.ShutdownTimeout` в `Program.cs`), грейс-период в compose 30 (`stop_grace_period`): хост перестаёт ждать раньше, чем процесс убьют.

Что попробовать:

1. Деплой посреди батча. `POST /chaos/mail/slow?seconds=3`, двадцать писем разом (`tools/seed.sql` с `-v n=20`: `docker compose exec -T db psql -U shop -v n=20 < tools/seed.sql`), и секунд через десять останови магазин: `docker compose stop shop`. Он останавливается за секунду-три. Начатое письмо уходит, остальные лежат в таблице без отметки (`tools/outbox.sql`). После `docker compose start shop` остальные уходят на первом тике. Писем в почте ровно двадцать, дублей нет.
2. Анти-пример `Mistakes__TokenInSave` (`Mistakes/TokenInSave.cs`): рассылка раздела 5, стоппинг-токен в сохранении отметки. Повтори п. 1, перед ним `docker compose down -v`. Письмо, которое шло в момент остановки, ушло, а сохранение отметки с отменённым токеном бросило исключение отмены. После старта это письмо приходит второй раз: в почте двадцать одно письмо, у двух одна тема. Дубли видно в веб-интерфейсе почты или одной командой. bash: `curl -s "http://localhost:8025/api/messages?pageSize=5000" | grep -o '"subject":"[^"]*"' | sort | uniq -d`. Остановка займёт меньше десяти секунд. Хост ждёт рассылку, рассылка ждёт только начатое письмо, а его на десятой секунде обрывает таймаут отправки. В логе `warn` с `OperationCanceledException`, у письма одна попытка (`tools/outbox.sql`). После старта оно уйдёт на следующей попытке, через минуту: медленная почта после рестарта снялась сама. До двадцати секунд `ShutdownTimeout` остановка здесь не доходит. Это предел для работы без своего таймаута, а у отправки он есть.

Дальше:

- Переопределяешь `StopAsync` у `BackgroundService`, вызови базовый (`await base.StopAsync(ct)`): он и отменяет стоппинг-токен, и ждёт `ExecuteAsync`. Иначе хост не дождётся рассылки.
- Сигнал остановки в контейнере. В shell-форме `CMD` или `ENTRYPOINT` (без квадратных скобок) приложение запускает оболочка, и SIGTERM достаётся ей. То же, если shell-скрипт запускает приложение без `exec`. .NET о сигнале не узнаёт, и оркестратор каждый раз убивает процесс по грейс-периоду. В `Dockerfile` проекта exec-форма: `ENTRYPOINT ["dotnet", "Shop.dll"]`.
- Kubernetes убирает под из балансировщика и в ту же секунду шлёт SIGTERM, так что пару секунд запросы ещё приходят. Поэтому перед остановкой ставят короткую паузу (`preStop`), а таймаут хоста считают от того, что осталось от грейс-периода. Нужно на остановку больше, поднимай и `terminationGracePeriodSeconds`, и `ShutdownTimeout`. Таймаут хоста должен оставаться меньше.
- IIS по умолчанию останавливает пул приложения после двадцати минут без запросов, и фоновые сервисы останавливаются вместе с ним до следующего запроса. Отключи остановку по простою (`idleTimeout = 0`), включи автозапуск пула и предзагрузку сайта. Или вынеси фоновую работу в отдельный сервис.

### 07-instances · Два инстанса сервиса

Что изменилось. Выборка LINQ ушла. Рассылка забирает батч себе одной командой `UPDATE … RETURNING` через `FromSql`. Подзапрос выбирает до двадцати писем по тем же условиям (не отправлено, попыток меньше пяти, время пришло) и блокирует их `FOR UPDATE SKIP LOCKED`. Строки, которые сейчас забирает другой инстанс, он пропускает и берёт следующие. `UPDATE` ставит взятым время следующей попытки на пять минут вперёд, это «взято до», и выборки других инстансов их не видят. Заказы батча догружаются отдельным запросом в тот же контекст: `Include` к команде `UPDATE` не прицепить, а контекст сам проставит каждому письму его заказ. Тик, scope, оба `try`, пауза в `ScheduleRetry` и отметка без токена остались как были. В `docker-compose.yml` появился второй инстанс `shop2` (профиль `copies`, порт 8082).

### 08-lease · Инстанс упал посреди батча

Что изменилось. Код рассылки тот же, что в разделе 7. «Взято до» и есть аренда: инстанс говорит базе не «моё навсегда», а «моё на пять минут». Упавший инстанс ничего не отдаёт, аренда выходит, и его письма сами возвращаются в общую очередь. Пять минут с запасом длиннее самого долгого батча: двадцать писем по десять секунд таймаута дают чуть больше трёх минут. Порядок «отправить, потом отметить» выбирает дубль, а не потерю: письмо, которое ушло без отметки, придёт второй раз. Новое на теге: сбой `/chaos/crash-after-send` и анти-пример короткой аренды.

3. Анти-пример `Mistakes__ShortLease` (`Mistakes/ShortLease.cs`): аренда тридцать секунд. Анти-пример нужен под `shop` и под `shop2`. Дальше:

- Вернуть невзятые письма батча сразу при остановке. Рассылка останавливается между письмами, и остаток батча ждёт аренду до пяти минут (п. 2). Его можно отдать сразу: перед выходом из цикла одна команда ставит оставшимся письмам `NextTryAt = now`, по их `Id`, с `CancellationToken.None`, как отметку. Тогда новый процесс заберёт их на первом тике.
- Письмо, которое само роняет процесс (огромное вложение, ошибка в шаблоне до `OutOfMemoryException`), уходит в аренду и роняет инстанс. Через пять минут его забирает следующий и тоже падает. Счётчик попыток здесь растёт только в `catch`, до которого падение не доходит. Защита: записывать попытку до отправки, прямо в команде «забрать батч» (`SET "Attempts" = "Attempts" + 1`). После пяти падений письмо выйдет из выборки. Цена: попытка сгорает и при обычном деплое посреди батча.
- Дубль письма в ящике. Некоторые почтовые провайдеры принимают ключ идемпотентности и второе письмо с тем же ключом не отправят. У обычного SMTP такого нет, но у письма есть заголовок `Message-ID`. Если ставить его из `Id` строки письма (`message.Headers.Add("Message-ID", $"<{p.Id}@shop.example>")`), некоторые почтовые ящики не покажут второе письмо с тем же `Message-ID`. Гарантии это не даёт: склейку делает ящик покупателя, а не магазин.

### 09-loops · Распродажа: несколько циклов

Что изменилось. В одном фоновом сервисе четыре цикла разбора (`Loops`): `ExecuteAsync` запускает их и ждёт все через `Task.WhenAll`. У каждого цикла свой `PeriodicTimer`, свой `try` и свой scope с контекстом на каждый проход. Развести циклы умеет та же команда со `SKIP LOCKED`: ей всё равно, чужой это инстанс или соседний цикл. Проход теперь возвращает, сколько писем забрал. Пришёл полный батч, и цикл берёт следующий сразу, без ожидания тика. Почтовый клиент по-прежнему свой на каждое письмо: `SmtpClient` шлёт одно письмо за раз.

Что попробовать:

1. Пик. `POST /chaos/mail/slow?seconds=1` (письмо уходит секунду, как у настоящего провайдера) и тысяча писем разом: `docker compose exec -T db psql -U shop -v n=1000 < tools/seed.sql`. Через минуту `tools/progress.sql` покажет, сколько ушло: четыре цикла ждут почту одновременно. Тот же опыт на теге `08-lease`, с одним циклом, даёт вчетверо меньше.
2. Анти-пример `Mistakes__SharedSmtpClient` (`Mistakes/SharedSmtpClient.cs`): один `SmtpClient` на всё приложение, по привычке к `HttpClient`. Тысяча писем без медленной почты. В логе `warn` с `InvalidOperationException: An asynchronous call is already in progress`, а в `tools/progress.sql` письма с попыткой, хотя почта жива. Пока клиент занят письмом одного цикла, письма соседних получают ошибку, и у них сгорает попытка.

Дальше:

- Порядок писем. Четыре цикла отправляют письма в том порядке, в каком закончат, и письма о разных заказах обгоняют друг друга. Если «заказ отменён» не должен обогнать «заказ принят», такие письма шлёт один цикл. Или у письма есть номер версии, и отправка проверяет, что прошлое ушло.
- Лимит провайдера в письмах в секунду держит рейт-лимитер (`System.Threading.RateLimiting`, например `TokenBucketRateLimiter`): цикл берёт разрешение перед каждой отправкой. Лимитер живёт в памяти процесса, поэтому при двух инстансах лимит провайдера делят между ними или ставят общий лимитер, например в Redis.
- Цикл без своего `try` под `Task.WhenAll` выбывает молча. Остальные три работают, рассылка становится медленнее, а ошибка дойдёт до хоста, только когда упадут все. Поэтому `try` стоит в каждом цикле (`LoopAsync`).
- Пул соединений. Клиент на письмо открывает новое соединение с почтой на каждое письмо. На большом потоке берут MailKit и держат несколько подключённых клиентов: каждый цикл шлёт письма подряд по своему соединению.
- Рассылку можно вынести в отдельное приложение на шаблоне Worker Service: тот же `BackgroundService`, тот же `AddHostedService`, только хост без веб-сервера. Но при выкатке старая и новая версии всё равно работают вместе, так что команда «забрать батч» нужна и там. Серверлес вроде Azure Functions работает на другой модели хостинга: функцию запускает платформа по таймеру или по сообщению, `BackgroundService` там нет.
- Число циклов и размер батча здесь константы. В проде их выносят в настройки (`IOptions<OutboxOptions>`): циклов столько, сколько выдержит почта, а это у каждого провайдера своё.

### 10-schedule · Задача по расписанию

Что изменилось. Второй фоновый сервис, `Background/OrderCleanupWorker.cs`, раз в минуту отменяет заказы, которые не оплатили за полчаса. Цикл тот же, что у рассылки: `PeriodicTimer`, `try` на проход с тем же фильтром по стоппинг-токену, свой scope. Сама отмена делается одной командой `ExecuteUpdate`. База меняет статус всем новым заказам старше получаса и возвращает, скольким поменяла, а заказы в память не грузятся. - Kubernetes CronJob запускает задачу по расписанию отдельным подом. Удобно для тяжёлых задач раз в сутки, но под стартует каждый раз заново, и раз в минуту так не делают.
- Отправленные письма копятся в таблице исходящих: частичный индекс выборки их не хранит, но таблица растёт. Их чистит та же задача второй командой: `ExecuteDeleteAsync` по письмам, отправленным больше тридцати дней назад.

### 11-race · Очистка и оплата в одну секунду

Что изменилось. Оплата написана как очистка: одна команда `ExecuteUpdate` с условием «заказ ещё `New`» (`Api/OrdersController.cs`, `Pay`). Поменялась одна строка, ответ 200. Ноль строк значит, что заказ уже оплачен или отменён, ответ 409. Заказа нет вовсе, 404. Кто первым изменил строку, тот и прав: второй получает ноль строк и ничего не перезаписывает. Привычная оплата прошлых тегов (загрузить, проверить, поменять, сохранить) ушла в анти-пример `Mistakes/LoadModifySavePay.cs`.

Что попробовать:

1. Анти-пример `Mistakes__LoadModifySavePay`, привычная оплата. Оформи заказ, состарь его (`tools/age-orders.sql`), включи `POST /chaos/pay/slow?seconds=70` и оплати: `POST /orders/{id}/pay`. Оплата загрузила заказ, проверила `New` и ждёт перед сохранением семьдесят секунд (в логе «смена статуса заказа ждёт 70 с»), то есть дольше, чем до следующего прохода очистки. За это время очистка отменяет заказ, в логе «Отменено заказов: 1». Оплата отвечает 200, и `GET /orders/{id}` показывает `Paid`: `SaveChanges` написал `UPDATE` по номеру заказа и перезаписал чужую отмену. Магазин отменил заказ, а покупатель за него заплатил.
2. Тот же опыт без анти-примера. На команду медленная оплата не действует: у неё нет загрузки и сохранения. Оплатишь до прохода очистки, получишь 200, и очистка оплаченный заказ не тронет. После прохода будет 409 «Заказ уже оплачен или отменён», деньги не взяты. Номер, которого нет, даёт 404.
3. Очистка, написанная так же, проигрывает наоборот: анти-пример `Mistakes__LoadModifySave` (`Mistakes/LoadModifySave.cs`). Состарь заказ, включи `POST /chaos/cleanup/slow?seconds=70` и дождись прохода очистки. В логе «смена статуса заказа ждёт 70 с перед сохранением»: очистка загрузила просроченные заказы и ждёт. Оплати заказ за это время, получишь 200, `Paid`. Через семьдесят секунд очистка сохраняет `Cancelled` поверх оплаты, и оплаченный заказ отменён. `POST /chaos/db/ok` снимает оба замедления.

Дальше:

- Отмена с письмом покупателю. Если с отменёнными нужно что-то сделать (написать покупателю, вернуть товар на склад), команда возвращает их номера, и действие ложится строкой в таблицу исходящих в той же транзакции:

  ```csharp
  await using var tx = await db.Database.BeginTransactionAsync(ct);
  var ids = await db.Database.SqlQuery<Guid>($"""
      UPDATE "Orders" SET "Status" = {(int)OrderStatus.Cancelled}
      WHERE "Status" = {(int)OrderStatus.New}
        AND "CreatedAt" < {deadline}
      RETURNING "Id" AS "Value"
      """).ToListAsync(ct);
  // по строке письма «заказ отменён» на каждый номер из ids
  await db.SaveChangesAsync(ct);
  await tx.CommitAsync(ct);
  ```

  Упала транзакция, и нет ни отмены, ни писем. Прошла, значит, есть и то, и другое, как у заказа и письма в разделе 2.
- Цена одной команды: она идёт мимо `SaveChanges`, его перехватчиков и логики в сущности. Если отмена держится на этой логике, отменяй заказы по одному, каждый в своём контексте, а статус сделай concurrency-токеном. В Npgsql для этого есть системная колонка версии строки `xmin` (`b.Entity<Order>().Property<uint>("xmin").IsRowVersion()`). Если заказ успели оплатить, `SaveChanges` бросит `DbUpdateConcurrencyException`, и этот заказ ты пропустишь.
- Здесь оплата приходит запросом к магазину. В жизни деньги списывает платёжный сервис, и статус меняет обработчик его подтверждения. Проверь подпись подтверждения, меняй статус с тем же условием на `New`, а когда условие не сработало, возвращай деньги.
- Npgsql и `DateTime`. Колонки времени здесь `timestamp with time zone`, и Npgsql пишет в них только `DateTime` с `Kind = Utc`, а `Local` и `Unspecified` отвергнет. Держи время в UTC (`DateTime.UtcNow`), а в пояс магазина переводи при показе (раздел 12).

### 12-nightly · Отчёт ровно в три ночи

Что изменилось. Отчёт о продажах за вчера считает третий фоновый сервис, `Background/DailySalesWorker.cs`. Время следующего запуска лежит строкой в таблице расписания (`Data/ScheduledJob.cs`, строка `daily-sales`): её видят оба инстанса, и она переживает рестарт. Раз в минуту каждый инстанс пробует сдвинуть это время на ближайшие три ночи одной командой с условием «время пришло». Сдвинул, значит, считает он. Ноль строк значит, что посчитал сосед или время не пришло. Сдвиг и запись отчёта (`DailySales`) идут одной транзакцией: упал посреди подсчёта, и сдвиг откатится. Сосед, который пришёл в ту же секунду, ждёт блокировку строки и перепроверяет условие на новой версии, а не пропускает её, как `SKIP LOCKED` у писем: строка отчёта одна. Три ночи считаются по времени магазина (`Shop:TimeZone` в настройках, в проекте `Europe/Moscow`), в базе время по UTC, перевод через `TimeZoneInfo`. Строка расписания создаётся вместе с базой (`HasData`) со временем в прошлом, поэтому первый же тик после старта считает отчёт.

Что попробовать:

1. Свежий старт. Через минуту после старта в логе «Отчёт за …: заказов 0»: строка создалась со временем в прошлом. В `tools/report.sql` следующий запуск стоит на ближайшие 03:00 по Москве, а отчёт посчитан за вчера.
2. Два инстанса и один отчёт. Подними `--profile copies`, положи оплаченные заказы за вчера (`tools/sales-yesterday.sql`, пять заказов на 4500 ₽) и сделай вид, что три ночи наступили: `tools/report-due.sql` ставит время запуска в прошлое. На ближайшем тике «Отчёт за …: заказов 5, выручка 4500 ₽» пишет только один инстанс. В `tools/report.sql` прибавилась одна строка, а следующий запуск снова стоит на ближайшие 03:00.
3. Обслуживание: `tools/report-due.sql`, сразу `docker compose stop shop` и через пару минут `docker compose start shop`. Пока магазина нет, отчёт никто не считает. Первый тик после старта видит время в прошлом, и отчёт проходит с опозданием, а не пропадает.
4. Анти-пример `Mistakes__DailyTimer` (`Mistakes/DailyTimer.cs`): `PeriodicTimer` на сутки. На старте анти-пример пишет в лог, когда придёт первый отчёт: ровно через сутки после старта, а не в три ночи. Подними второй инстанс минутой позже, и у него свои сутки и свой отчёт за тот же день.

Дальше:

- Пояс в контейнере. `TimeZoneInfo.FindSystemTimeZoneById("Europe/Moscow")` на Linux читает базу поясов из `/usr/share/zoneinfo`. В образе `mcr.microsoft.com/dotnet/aspnet` она есть, в chiseled-образах только в вариантах `-extra`. Имена берутся из IANA (`Europe/Moscow`), на Windows .NET 6+ переводит их в свои сам.
- Летнее время. В поясах с переходом час 02:00–03:00 бывает дважды или не бывает вовсе. `ConvertTimeToUtc` для несуществующего часа бросает `ArgumentException`, для двойного выбирает один из двух. В Москве перехода нет. В поясе с переходом ставь задачу на час, который точно есть, или проверяй `zone.IsInvalidTime(next)`.
- Расписание строкой. Когда задач несколько и у каждой своё «по будням в 9:00», расписание записывают cron-выражением, а следующий запуск считает библиотека Cronos (`CronExpression.Parse("0 3 * * *").GetNextOccurrence(now, zone)`) вместо `NextThreeAm`.
- Та же задача на Quartz: `IJob` с `[DisallowConcurrentExecution]`, триггер `WithCronSchedule("0 0 3 * * ?", x => x.InTimeZone(zone))` и хранилище в базе с кластеризацией (`UsePersistentStore(... UseClustering())`). Quartz сам следит, чтобы запуск достался одному узлу, и помнит пропущенные. Бери его, когда задач десятки и нужны история запусков и панель.
- Догон нескольких дней. Магазин простоял трое суток, а отчёт придёт один, за вчера: команда сдвигает время сразу на ближайшие три ночи. Нужны все пропущенные дни, сдвигай `NextRunAt` на сутки вперёд, а не на ближайшие три ночи, и считай день `NextRunAt`. Каждый следующий тик догонит ещё один день. Или прими пропуск осознанно и посчитай пропущенное руками.
- Вторая защита от дубля: уникальный индекс по дню в `DailySales` (`b.Entity<DailySale>().HasIndex(s => s.Day).IsUnique()`). Если отчёт за день как-то посчитают дважды, вторая запись упадёт, а транзакция откатит и сдвиг.
- Kubernetes CronJob: отчёт отдельным подом по расписанию `0 3 * * *` (с `timeZone: Europe/Moscow` с Kubernetes 1.27). Тогда отчёт не живёт в магазине, но одного запуска нужно добиться так же. Нужен `concurrencyPolicy: Forbid`, а под может стартовать дважды, так что нужна и та же строка с условием или уникальный индекс.

### 13-export · Выгрузка, которую запускает менеджер

Что изменилось. Появилась выгрузка заказов за период в CSV (`Api/ExportsController.cs`).

- `POST /exports` считает, сколько заказов попадёт в выгрузку (один `count`), пишет строку выгрузки (`Data/Export.cs`) и сразу отвечает `202 Accepted` с адресом статуса в заголовке `Location`.
- `GET /exports/{id}` отдаёт статус, сколько выгружено из скольких и, когда готово, адрес файла. `GET /exports/{id}/file` отдаёт только готовый файл. `POST /exports/{id}/cancel` отменяет выгрузку командой с условием на статус.

Работу делает четвёртый фоновый сервис, `Background/ExportWorker.cs`. Раз в пять секунд он забирает выгрузку (ждущую или ту, чья аренда вышла) той же командой со `SKIP LOCKED`, что и письма, и ставит аренду на минуту и свою метку (`LeaseToken`, новый `Guid` на каждую попытку). CSV пишется частями по тысяче заказов прямо в файл этой попытки (`{id}.{метка}.part`). После каждой части сервис пишет прогресс и продлевает аренду одной командой с условием «ещё `Running`, и метка моя». Выгрузку отменили или забрал другой инстанс, потому что часть писалась дольше аренды: команда вернёт ноль строк, и сервис бросит работу. Файл, записанный целиком, получает имя выгрузки (`{id}.csv`), а `Done` ставится тем же условием, так что успевшая раньше отмена не затрётся. Не сработало условие, в логе «Выгрузка … не закончена».

Части идут по ключу `(CreatedAt, Id)`: следующая начинается после последнего заказа прошлой. `Skip` заново проходил бы все пропущенные строки, и на большой таблице выгрузка росла бы квадратом. Для частей и для `count` есть индекс `(CreatedAt, Id)` (`Data/AppDb.cs`). Статус выгрузки хранится строкой (`HasConversion<string>`): его сравнивает сырой SQL. Файлы лежат в общем томе `exports` у обоих инстансов. В compose перед магазином появился прокси `proxy`, http://localhost:8088: он ждёт ответа минуту и отдаёт 504.

Что попробовать:

1. Положи заказы для выгрузки: `tools/seed-export.sql`, 12 000 за октябрь 2026 и 11 000 за сентябрь. Сделай части медленными, чтобы успеть посмотреть: `POST /chaos/export/slow?seconds=5`.
2. Выгрузка за октябрь: `POST /exports` с телом из `tools/export-october.json`. Ответ 202 приходит сразу, в `Location` адрес статуса, в теле `total: 12000`. Открывай статус: `Running`, `processed` растёт по тысяче.
3. Отмена. На середине `POST /exports/{id}/cancel`, ответ 202. Статус `Cancelled`, `processed` больше не растёт: следующее обновление прогресса вернуло ноль строк. Файл этой выгрузки не отдаётся, 404. Отменить ещё раз нельзя, 409.
4. Выгрузка за сентябрь (`tools/export-september.json`). Дождись `Done`: в статусе адрес файла, по нему CSV на 11 000 строк и заголовок.
5. Деплой посреди выгрузки. Два инстанса: `docker compose --profile copies up -d --build` (сборка нужна обоим), медленные части на обоих (`/chaos/export/slow` на 8080 и 8082), новая выгрузка за октябрь. Посмотри в логе, какой инстанс написал «Выгрузка … взята», и останови его (`docker compose stop shop` или `shop2`). В строке осталось `Running` и аренда на минуту вперёд. Когда аренда выйдет, второй инстанс заберёт выгрузку (в его логе «взята») и построит её заново, с первой части и в свой файл: прогресс откатывается и растёт снова.
6. Часть дольше аренды. Два инстанса, как в п. 5, но `shop2` пока остановлен: `docker compose stop shop2`. На `shop` сделай часть дольше аренды (`POST /chaos/export/slow?seconds=70`), запусти выгрузку за октябрь и дождись в логе `shop` «Выгрузка … взята». Подними `shop2` (`docker compose start shop2`) и дай ему части побыстрее: `POST http://localhost:8082/chaos/export/slow?seconds=5`. Первая часть у `shop` пишется семьдесят секунд, аренда на минуту выходит раньше, и `shop2` забирает выгрузку со своей меткой (в его логе «взята»). Когда `shop` дописал часть, его обновление прогресса находит в строке чужую метку и возвращает ноль строк, и `shop` бросает работу. `processed` растёт только по частям `shop2` и не откатывается, `Done` и файл получаются от `shop2`. Брошенный файл попытки `shop` (`.part`) остаётся в томе, под имя выгрузки он не попадает.
7. Анти-пример `Mistakes__ExportInRequest` (`Mistakes/ExportInRequest.cs`): выгрузка прямо в запросе. `POST /chaos/export/slow?seconds=10` и выгрузка за октябрь через прокси: `POST http://localhost:8088/exports`. Ровно через минуту прокси отвечает 504, а в логе магазина «Выгрузка в запросе: … из 12000» идёт дальше. Токена в выгрузке нет, и сервер делает работу, которую никто не дождётся. Повтори запрос, и на сервере идут две выгрузки сразу.

Дальше:

- Файл в объектном хранилище. Общий том хорош для compose. В облаке файл кладут в blob-хранилище (S3, Azure Blob) частями, а скачивание отдают ссылкой с ограниченным сроком, и инстансу не нужно гнать файл через себя.
- Опрос статуса раз в несколько секунд прост и переживает рестарты. Если менеджер должен видеть прогресс мгновенно, сервис шлёт его через SignalR в группу выгрузки. Но источником правды остаётся строка в таблице: после переподключения страница читает статус по адресу.
- Старые выгрузки и их файлы копятся. Их чистит задача по расписанию (раздел 10): строки `Done` и `Cancelled` старше недели одной командой, файлы по их номерам, вместе с брошенными файлами попыток (`{id}.*.part`).
- Проверка периода: `From` раньше `To`, и период не длиннее, скажем, года, иначе 400 до записи строки. Здесь её нет, чтобы не заслонять фон.

### 14-channel · Канал для того, что можно потерять

Что изменилось. Страница товара (`GET /products/{id}`, `Api/ProductsController.cs`) кладёт просмотр в канал и не ждёт: `TryWrite` положил и ответил. Канал (`Background/ProductViews.cs`) один на приложение, singleton. Он ограничен тысячей просмотров, режим `DropOldest`: когда канал полон, новый просмотр вытесняет самый старый. Наружу канал отдаёт две половины: писателя странице, читателя сервису, а флаг `SingleReader` говорит ему, что читатель один. Пятый фоновый сервис, `Background/ViewsWriter.cs`, ждёт, пока в канале что-то появится, забирает всё, что лежит, но не больше ста, и пишет в базу одним `SaveChanges`. «Популярное» за последний час отдаёт `GET /products/popular`. Индекс по времени просмотра (`Data/AppDb.cs`) даёт ему читать только последний час, а не всю таблицу. Товары 1–100 создаются вместе с базой, под номером 77 кружка. У контейнера магазина теперь лимит памяти 512 МБ, как у пода в Kubernetes.

Что попробовать:

1. Открой `GET /products/77` несколько раз и `GET /products/popular`. Просмотры уже в базе, а страница за ними в базу не ходила.
2. База занята, поток просмотров. `POST /chaos/db/slow-views?seconds=30` (запись пачки ждёт полминуты) и `POST /chaos/views/flood?count=5000000`, пять миллионов просмотров разом. `GET /chaos/views`: в канале тысяча, память процесса та же, страница товара отвечает так же быстро. Лишние просмотры вытеснены, и «Популярное» посчитано по последним. Это цена, известная заранее.
3. Рестарт: `docker compose restart shop`. Тысяча просмотров из канала потеряна, магазин этого не заметил.
4. Анти-пример `Mistakes__UnboundedViews` (`Mistakes/UnboundedViews.cs`): канал без лимита. Повтори п. 2. В канале все пять миллионов, память выросла на сотни мегабайт (`GET /chaos/views`). Добавь ещё пару раз по три миллиона. Процесс упирается в лимит контейнера, в логе `OutOfMemoryException`, и магазин падает, а вместе с просмотрами падают приём заказов и рассылка. Docker поднимает его заново, а всё, что лежало в канале, пропало.

Дальше:

- Почему не `BlockingCollection`. Она тоже с пределом и тоже ждёт, но ждёт, держа поток пула: и читатель пустой очереди, и писатель в полную. На распродаже это десятки занятых потоков, пул добавляет новые не сразу, и соседние запросы отвечают секундами. Канал ждёт через `await` и поток отпускает.
- Число вытесненных тоже метрика. У `Channel.CreateBounded` есть перегрузка с колбэком `itemDropped`, он вызывается на каждый выброшенный элемент. Посчитай их счётчиком и отдай в метрики, чтобы видеть, когда «Популярное» считается не по всем просмотрам.
- Остановка. На остановке хост отменяет стоппинг-токен, `WaitToReadAsync` выходит, и то, что лежало в канале, теряется. Остаток можно дописать: на остановке закрыть канал (`Writer.Complete()` в `StopAsync` сервиса, до `base.StopAsync`), дочитать его до конца и записать последнюю пачку без стоппинг-токена, так же, как отметку письма в разделе 6.
- Канал как звонок для рассылки. Письма лежат в таблице, и рассылка ждёт тик до пяти секунд. Если задержка мешает, контроллер после сохранения заказа кладёт в канал «проверь таблицу», а цикл рассылки ждёт звонка, но не дольше тика. Звонок потерялся, а письмо всё равно уйдёт по тику: данные в базе, канал только будит.
- Просмотры копятся. На распродаже это миллионы строк в день, а «Популярному» нужен только последний час. Старые чистит задача по расписанию (раздел 10) одной командой: `ExecuteDeleteAsync` по `ViewedAt` старше, например, суток. Индекс по `ViewedAt` помогает и ей.
- TPL Dataflow (`System.Threading.Tasks.Dataflow`) строит цепочки блоков с буферами и параллельностью: `BatchBlock` сам собирает пачки по сто, `ActionBlock` пишет их в базу. Для одного писателя и одного читателя канал проще.

### 15-health · Жив ли фоновый сервис

Что изменилось. Хелсчеки смотрят не на процесс, а на сделанную работу. `Background/OutboxHealthCheck.cs` проверяет рассылку. Самое старое неотправленное письмо ждёт больше десяти минут, и ответ `Degraded`. Есть письма после пяти ошибок, тоже `Degraded`, и этот ответ держится, пока их не разберут (команда возврата или удаление строки). Десять минут выбраны между паузами повтора: после двух ошибок письмо пробует снова на пятой минуте, а третья ошибка отодвигает попытку на четырнадцатую. Контекст базы проверка берёт прямо в конструкторе: сервис хелсчеков создаёт её заново на каждый прогон, в своём scope. Очистка после каждого успешного прохода пишет время в singleton `CleanupStatus` (через `Interlocked`: пишет один поток, читает другой), и `CleanupHealthCheck` отвечает `Degraded`, если прохода не было три минуты. Регистрация: `AddHealthChecks` в `Program.cs`, адрес `/health`.

Что попробовать:

1. `GET /health` отвечает `Healthy`.
2. Почта лежит: `POST /chaos/mail/down` и заказ. Пару минут `/health` отвечает `Healthy`: письмо на паузе, это может быть временная ошибка. Чтобы не ждать десять минут, состарь неотправленные письма: `tools/age-outbox.sql`. Теперь `/health` отвечает `Degraded`, а в логе видно, какая проверка и почему: `Health check email-outbox with status Degraded … 'Письмо не уходит больше десяти минут'`. Обрати внимание на код ответа: 200. Об этом раздел 16.
3. Подними почту (`POST /chaos/mail/up`) и не жди паузу: `tools/skip-wait.sql`. Письмо уходит на ближайшем тике, `/health` снова `Healthy`.
4. Письмо, которое сдалось: заказ из `tools/order-typo.json` и четыре раза `tools/skip-wait.sql` после тика (как в разделе 5). Ответ `Degraded` «Писем после пяти попыток: 1» держится, пока строку не удалят или адрес не исправят.
5. Очистка: `POST /chaos/cleanup/fail`. Проход очистки падает на каждом тике, в логе раз в минуту «Очистка заказов упала». Через три минуты после последнего успешного прохода `/health` отвечает `Degraded`, «Очистка стоит 3 мин». После `POST /chaos/db/ok` на ближайшем проходе снова `Healthy`.

Дальше:

- `/health` по умолчанию отвечает одним словом, а `data` проверки в ответ не попадает. Чтобы видеть причины и числа (возраст старого письма, сколько сдавшихся), задай `ResponseWriter` в `HealthCheckOptions` и пиши отчёт в JSON. Или отдай те же числа метриками.
- Длина таблицы писем мало что говорит: на распродаже она длинная и при живой почте. Смотри на возраст самого старого письма. Он растёт, только когда письма не уходят.
- Время прохода очистки лежит в памяти инстанса, и у каждого инстанса своя проверка. За балансировщиком `/health` отвечает тот инстанс, на который попал запрос, поэтому мониторинг опрашивает каждый инстанс по его адресу, а не общий адрес: так видно, в каком встала очистка. Проверки по таблице, наоборот, у всех инстансов дают один ответ.
- Хелсчек выгрузок делается тем же приёмом: выгрузка `Running`, чья аренда вышла, а её никто не забрал, даёт `Degraded` «сервис выгрузок стоит».
- Хелсчек отчёта: после 03:30 по времени магазина за вчера нет строки в `DailySales`, и ответ `Degraded` «отчёт не посчитан».

### 16-live · Алерт или перезапуск

Что изменилось. У хелсчеков два адреса (`Program.cs`). На `/health` работают все проверки, и `Degraded` на нём отвечает 503, а не 200, как по умолчанию. На него смотрит мониторинг и будит дежурного. `Unhealthy` отдал бы 503 и сам, но он значит «сломано всё», а у нас встала часть работы. Поэтому проверка остаётся `Degraded`, а код ей назначен через `ResultStatusCodes`. На `/health/live` проверок нет (`Predicate = _ => false`), он отвечает 200, пока процесс жив. На него вешают пробу живости, балансировщик и readiness-пробу. Перезапуск лечит процесс, а почту не лечит: проба живости на `/health` перезапускала бы магазин по кругу, пока лежит почта.

Что попробовать:

1. `GET /health` и `GET /health/live`: оба `Healthy`, 200.
2. `POST /chaos/mail/down`, заказ и `tools/age-outbox.sql` (вместо десяти минут ожидания). `/health` отвечает `Degraded` и 503, и алерт по коду ответа это видит. `/health/live` отвечает `Healthy`, 200: процесс жив, перезапускать его не за что, заказы принимаются.
3. Сравни с тегом `15-health`: там тот же опыт даёт `Degraded` с кодом 200, и мониторинг, который смотрит на код, промолчал бы.
4. Подними почту и не жди паузу: `POST /chaos/mail/up`, `tools/skip-wait.sql`. Письмо уходит, `/health` снова отвечает 200.
5. В Kubernetes проба живости вешается на `/health/live`:

   ```yaml
   livenessProbe:
     httpGet: { path: /health/live, port: 8080 }
     periodSeconds: 10
     failureThreshold: 3
   readinessProbe:
     httpGet: { path: /health/live, port: 8080 }
   ```

   Повесь `livenessProbe` на `/health`, и при лежащей почте под перезапускается каждые полминуты: новый процесс видит то же старое письмо и сразу отвечает 503. docker compose по своей `healthcheck` контейнер только помечает `unhealthy` и не перезапускает.

Дальше:

- Кто опрашивает `/health` и шлёт алерт. Внешний мониторинг (Prometheus с blackbox exporter, Uptime Kuma, облачный мониторинг). Или `IHealthCheckPublisher` в самом приложении: он раз в период прогоняет проверки и отдаёт отчёт, куда скажешь. Или те же значения метриками через OpenTelemetry.
- Readiness и проба запуска живут отдельно от `/health`. Readiness отвечает на вопрос «можно ли слать этому инстансу запросы», и туда идёт только то, без чего инстанс не обслужит запрос (своя база, прогрев). Проверки фоновой работы читают общую таблицу, у всех инстансов результат один, и на 503 из ротации вышли бы все разом. Startup-проба даёт медленному старту время, пока liveness не начала проверять.
- Служебные адреса (`/health`, `/outbox/given-up/retry`, `/chaos/...`) наружу не открывают. Их выносят на отдельный порт (`app.MapHealthChecks(...).RequireHost("*:8081")` и второй адрес в `ASPNETCORE_URLS`) или закрывают авторизацией. `/chaos` в этом проекте нужен только для стенда.
